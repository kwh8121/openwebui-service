## 1. Context

- 직전 사이클(`docs/plan/v0.11.1-integration.md`)로 upstream `v0.11.1`을 fork에 통합, `v0.11.1-kwh.1` → OAuth 서브젝트 SQLite 정수 오버플로 핫픽스 `v0.11.1-kwh.2`까지 프로덕션 배포 완료. 현재 프로덕션 이미지는 `ghcr.io/kwh8121/openwebui-service:v0.11.1-kwh.2` (`main` @ `3234ff6f5`).
- upstream `open-webui/open-webui`가 2026-08-31에 `v0.11.2`와 `v0.11.3`을 **같은 날 연속 릴리스**했다. fork는 2개 패치 버전 뒤처져 있다.
- Linear 프로젝트 `openwebui v0.11.3`은 아직 없다 (`openwebui v0.11.1`은 존재). 본 사이클에서 신규 생성한다.
- **목표 버전은 `v0.11.3` (v0.11.2 건너뜀)**. 근거는 §3.1.

## 2. 목표

- upstream `v0.11.3` 소스를 fork에 병합하고 fork 고유 커스터마이징을 무손실로 보존한다.
- 5-stage 워크플로(Linear stage 1~4 + GitHub stage 5)를 정상 경로로 통과한다.
- v0.11.2 보안 권고를 프로덕션에 조기 반영한다.
- 로컬 프로덕션 미러 게이트(`docs/plan/local-test-workflow.md`)를 RC·최종 태그에 대해 두 번 통과한 뒤에만 프로덕션에 배포한다.
- **이번 세션 스코프**: stage 1~4 중 **로컬 병합 + 로컬 검증까지만**. RC 태그·push·PR·배포는 다음 세션. (사용자 지시)

## 3. upstream v0.11.2 + v0.11.3 임팩트 요약

`git show upstream/v0.11.3:CHANGELOG.md` (v0.11.2, v0.11.3 섹션) 기반 fork 관점 요약.

### 3.1 v0.11.3을 목표로 하는 이유 (v0.11.2 건너뜀)

| 항목 | 내용 |
| ---- | ---- |
| **업그레이드 fail-safe 수정 (#29280)** | v0.11.3은 "DB 업그레이드가 절반만 적용된 채 시작되어 나중에 `chat.timer_at` 같은 누락 컬럼 오류를 내는" 문제를 수정 — CHANGELOG가 **"0.11.0, 0.11.1, 0.11.2에서 올라올 때 보이는 업그레이드 실패"**로 명시. fork는 0.11.1-kwh.2에 있으므로 **직접 관련**. v0.11.2를 중간 경유하면 이 위험 경로를 한 번 더 타는 셈. |
| 마이그레이션 실체 | **v0.11.1 → v0.11.3 사이 신규 Alembic/내부 마이그레이션 = 0건.** `main`과 `upstream/v0.11.3`의 `backend/open_webui/migrations/` · `internal/` 트리가 **완전히 동일**. v0.11.3의 수정은 마이그레이션 *에러 처리* 로직이지 새 스키마가 아니다. |
| 결론 | v0.11.2를 별도 사이클로 분리할 실익 없음. `v0.11.3` 한 번에 병합. |

## 7. Stage 3 (개발) — 병합 전략

### 7.1 브랜치 흐름

```
integration/v0.11.3  (main 기점 신규 생성)
  ↑ feature/docs-plan-v0.11.3-integration (--no-ff)   ← 본 문서
  ↑ feature/upstream-merge-v0.11.3 (--no-ff)          ← upstream 병합 + 충돌 해결
       └ git merge upstream/v0.11.3
  ↑ feature/customization-reverify-v0.11.3 (--no-ff, 필요 시)  ← release*.yml 재비활성화 등
  ↓ (stage 4 로컬 게이트 통과 후)
main (via PR)  ← 다음 세션
```

`AGENTS.md` §"Release Routine And Session Continuity":

- 절대 `main` 직접 커밋 금지
- 모든 변경(문서 포함) `feature/* → integration/vX.Y.Z → PR → main`

### 7.2 병합 방식

**`git merge upstream/v0.11.3` 태그 직접 병합.** 충돌 2건뿐으로 rebase 불필요·비권장(111 커밋). upstream 태그는 `refs/tags/upstream/v0.11.3` 네임스페이스로 분리 저장(fork 동명 태그 clobber 회피).

### 7.3 병합 커맨드 (참고)

```bash
# 준비
git fetch upstream --no-tags
git fetch upstream refs/tags/v0.11.3:refs/tags/upstream/v0.11.3
git fetch origin --prune

# integration 브랜치
git checkout main && git pull --ff-only
git checkout -b integration/v0.11.3
# (plan 문서 feature 브랜치 → --no-ff merge, 생략 가능하면 여기서 직접)

# 병합 feature 브랜치
git checkout -b feature/upstream-merge-v0.11.3
git merge upstream/v0.11.3
# 충돌: .github/workflows/docker.yaml, backend/open_webui/models/users.py
git checkout --ours .github/workflows/docker.yaml && git add .github/workflows/docker.yaml
# users.py: upstream 블록(17cc5667) 채택, 우리 2^63 가드 라인 제거 → 수동 편집 후 add
git commit

# 병합 후 재적용
git rm .github/workflows/release-pypi.yml .github/workflows/release.yml  # upstream 재도입분
git mv ... 또는 .disabled 상태 재생성   # release*.yml.disabled 유지
git commit -m "ci: re-disable upstream publish workflows for v0.11.3"

# integration 통합
git checkout integration/v0.11.3
git merge --no-ff feature/upstream-merge-v0.11.3
```
